# Rejeu : linux-reseau-securite
Verdict : ⚠️ faisable avec contournements
Machine : Ubuntu 24.04 vierge avec systemd PID 1 (lb-reseau, `new-vm.sh`) · Durée réelle : ~20 min (annoncée 195) · Étapes rejouées : 6/6

Prérequis : le guide déclare `linux-boot-systemd` ; aucune ressource de ce guide n'est réutilisée, rien à recréer. Seul `sudo apt update && sudo apt install -y bind9-dnsutils openssh-server ufw` a été joué. Juste après l'installation : `ssh.socket` actif, `ssh.service` inactif (activation par socket, conforme au guide).

Toutes les commandes passent sur la VM de test. Les écarts 1 à 3 concernent le cas où l'étudiant suit le guide **sur un serveur distant** (VPS, serveur d'entreprise), malgré la recommandation Multipass de l'intro. Le guide le recommande « fortement » sans l'imposer, et ces étapes peuvent alors couper l'accès SSH sans avertissement suffisant.

## Non testable ici
- step-01 : `ping -c 3 1.1.1.1` → `100% packet loss` : pas d'ICMP sortant dans le bac à sable. L'interface s'appelle `eth0@if63` (paire veth Docker) et non `enp0s…`/`ens…` comme sur une VM ; `eth0` dans l'exemple du guide reste plausible sur Multipass.
- step-03 : `/etc/resolv.conf` et `/etc/hosts` sont gérés par Docker (`nameserver 8.8.8.8`, pas le stub `127.0.0.53` annoncé) et `/etc/hosts` est un montage : `sudo sed -i '/monserveur.test/d' /etc/hosts` → `sed: cannot rename /etc/sedFj5RJZ: Device or resource busy` (l'entrée reste). Limite du bac à sable : sur une VM, `sed -i` sur `/etc/hosts` fonctionne et `resolv.conf` pointe vers `127.0.0.53`.
- step-04/05 : pas d'accès SSH entrant depuis l'extérieur. Tests faits en `ssh localhost` seulement. Les risques de coupure à distance (écarts 1 à 3) sont établis par analyse des commandes, et le refus du mot de passe après step-05 a été constaté en local.
- step-06 : pas d'IPv6 dans le noyau ; ufw fonctionne en IPv4 seul (aucune ligne `(v6)`), sans contournement nécessaire. Le filtrage depuis l'extérieur n'est pas vérifiable (pas d'IP publique).
- Pas de redémarrage réel : la persistance d'ufw (« enabled on system startup ») et de la config sshd après reboot n'est pas vérifiée.

## Leçon pour CHECKLIST section B (si nouveau type d'erreur)
- **Une vérification de sécurité doit tester le vrai chemin d'accès.** Tester une clé SSH vers `localhost` ne prouve pas que le poste de l'étudiant peut se connecter. Avant de couper un mode d'accès (mot de passe, root, port), le guide fait tester une **nouvelle** connexion depuis le poste client, dans un second terminal, en gardant la session ouverte.
- **Pas de `--force`/`-y` qui supprime un garde-fou natif** (`ufw --force enable`, `apt -y` sur un `remove`…) dans une étape qui peut couper l'accès, sauf si le guide reproduit l'avertissement et la vérification préalable (ici : le port SSH réel).
- **Tout guide qui modifie la sécurité système a un bloc de retour arrière** (fichiers de surcharge à supprimer, `ufw disable`, reload).
