# Rejeu : linux-utilisateurs-permissions
Verdict : ⚠️ faisable avec contournements
Machine : Ubuntu 24.04 vierge (new-vm.sh, systemd PID 1, `la-perms`) · Durée réelle : ~7 min d'exécution machine, lecture non comptée (annoncée 175) · Étapes rejouées : 7/7 + ménage final

Méthode : commandes lancées dans un vrai shell de connexion (`docker exec la-perms su - etudiant -c '...'`, donc `$USER=etudiant` et `umask 0002` comme sur une vraie session Ubuntu). Prérequis `linux-paquets` / `linux-fondamentaux` : aucun état à recréer, le guide crée lui-même `alice`, `bob`, `devs` (dépendances internes au guide, dans l'ordre). Le paquet `acl` était absent du bac à sable et s'est installé par le bloc de prérequis.

Toutes les commandes passent telles qu'écrites. Les écarts portent sur des affirmations du guide que la machine contredit.

## Leçon pour CHECKLIST section B (si nouveau type d'erreur)
- **Pas de démo de droits entre utilisateurs dans `/tmp`.** Ubuntu active `fs.protected_regular=2` : dans un dossier sticky partagé, un utilisateur ne peut pas ouvrir en écriture le fichier d'un autre, même avec une ACL ou un groupe qui l'autorise. Utiliser un dossier dédié (`/srv/lab`) et **prouver** l'effet annoncé en écrivant en tant qu'un autre utilisateur (`sudo -u alice …`). *(Bug réel : linux-utilisateurs-permissions step-06.)*
- **Une délégation se teste sur un service présent.** Une règle sudo, un timer ou un exemple de service doit viser une unité présente sur une machine neuve (`cron`), pas `ssh` (absent sans `openssh-server`).
